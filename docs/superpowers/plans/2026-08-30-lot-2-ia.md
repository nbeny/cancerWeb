# Lot 2 — IA — Plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Générer des idées, des plans et des brouillons d'articles par IA, dans un pipeline persisté, rejouable et réversible — sans toucher aux garanties établies aux lots précédents.

**Architecture:** Une abstraction `AIProvider` bas niveau (trois implémentations), un `AITaskService` métier écrit une seule fois au-dessus, et un pipeline en machine à états dont chaque étape persiste son résultat. Le worker est un process séparé, concurrence 1, imposée par l'agent CLI.

**Tech Stack:** BullMQ + Redis (déjà dans le compose) · `opencode` (validé en non-interactif) · le socle des Lots 0 et 1.

**Référence :** `docs/superpowers/specs/2026-08-30-lot-2-ia-design.md`

---

## Méthode

Comme au Lot 1 : code complet là où c'est nouveau ou piégeux (contrat CLI, validation d'outline, machine à états du pipeline, file d'attente), contrats de test explicites partout, et renvoi aux motifs établis du dépôt pour le répétitif.

**Ce qui existe et doit être réutilisé, pas réécrit :**

| Besoin | Ce qui existe déjà |
|---|---|
| Parser un plan Markdown | `apps/api/src/markdown/` — `parse`, `extractHeadings`, `splitSections` |
| Calculer un score SEO | `apps/api/src/seo/` — `analyze`, pur et déterministe |
| Rendre une écriture réversible | `VersionsService.snapshotBeforeAutomatedChange` — écrit, testé, sans consommateur |
| Créer un article depuis un topic | `ArticlesService.create` — transactionnel, passe le topic à `CONVERTED` |
| Motif service/resolver/module | `apps/api/src/domains/`, `apps/api/src/topics/` |
| Isolation par domaine | `@RequireDomainRole` + refiltrage systématique dans le service |
| Loader par requête | `apps/api/src/common/dataloader/loaders.ts` |

**Schéma Prisma — tout existe déjà, ne le modifie pas** : `PipelineRun`, `PipelineStep` (avec `attempt`, `input`, `output`, `heartbeatAt`), `AIJob` (avec `promptVersion`, `durationMs`, `rawOutput`, `correlationId`).

- [ ] **Step 2 : `FakeAIProvider` (tests d'abord)**

C'est **le provider le plus important du lot** : c'est lui qui tourne en CI, et toute la testabilité du pipeline en dépend.

Contrat :
- Retourne une fixture déterministe selon un marqueur présent dans le prompt (`[[OUTLINE]]`, `[[DRAFT]]`, `[[TOPICS]]`), afin que `AITaskService` n'ait pas à connaître le provider.
- `AI_FAKE_LATENCY_MS` simule une latence.
- `AI_FAKE_FAIL_STEP=DRAFT` fait échouer une étape précise, pour tester la reprise.
- `AI_FAKE_INVALID_OUTLINE=1` renvoie un plan invalide (deux H1), pour tester la relance.
- Deux appels identiques renvoient **exactement** le même texte — sans quoi les tests d'intégration seraient instables.

Tests : déterminisme, latence respectée, échec déclenché, plan invalide déclenché.

## Task 2 : `CliAgentProvider`

**Files:** `apps/api/src/ai/providers/cli.provider.ts` + spec

Le contrat a été établi empiriquement au premier jour (`docs/ai-cli-smoke-test.md`) : `opencode` n'expose ni `--prompt-file` ni `--output`.

- [ ] **Step 1 : Tests (ils doivent échouer)**

Teste contre un **faux binaire** (un script Node jetable écrit dans le répertoire temporaire), pas contre `opencode` : ces tests doivent tourner en CI, vite, sans dépendance externe.

Cas obligatoires :
- Prompt transmis par **stdin**, jamais en argument — vérifie-le en faisant écrire au faux binaire ce qu'il a reçu.
- Le résultat vient du **fichier `output.md`**, pas de stdout. Fais écrire au faux binaire du bruit sur stdout et un contenu différent dans le fichier : c'est le fichier qui doit gagner.
- Un binaire qui ne termine pas est tué au bout de `AI_CLI_TIMEOUT_MS`, et l'erreur le dit clairement.
- Un code de sortie non nul produit une erreur, avec stderr conservé dans `raw`.
- Un binaire qui ne crée pas `output.md` produit une erreur explicite, pas un texte vide.
- Le répertoire de travail est **supprimé après succès**, **conservé après échec**.
- Aucun `shell: true` : vérifie qu'un prompt contenant `; rm -rf /` n'exécute rien. C'est le test le plus important du fichier.

- [ ] **Step 2 : Implémenter**

```env
AI_CLI_COMMAND=opencode
AI_CLI_ARGS=["run","-m","{model}"]
AI_CLI_PROMPT_VIA=stdin
AI_CLI_TIMEOUT_MS=300000
AI_WORKSPACE_DIR=./.ai-workspace
```

`spawn` avec tableau d'arguments. `{model}` substitué depuis `AI_MODEL`. Prompt écrit dans `prompt.md` **et** transmis par stdin. Le prompt doit demander explicitement à l'agent d'écrire dans `output.md`.

Arrêt : `treeKill` ou équivalent — un `kill` sur le seul processus parent laisse l'agent tourner.

- [ ] **Step 3 : Test de fumée réel, exclu de la CI**

`apps/api/test/cli-provider.smoke-spec.ts`, avec un motif de nom que `jest.int.config.js` **n'inclut pas**. Documente comment le lancer à la main. Il exerce le vrai `opencode` ; il est lent et dépend d'un binaire local.

## Task 3 : Prompts et `AITaskService`

**Files:** `apps/api/src/ai/prompts/*.ts`, `apps/api/src/ai/ai-task.service.ts` + specs

- [ ] **Step 1 : Prompts versionnés**

Un fichier par tâche, exportant un identifiant de version et une fonction de construction :

```ts
export const OUTLINE_PROMPT_VERSION = 'OUTLINE_V1'
export function buildOutlinePrompt(domain: Domain, topic: Topic): string
```

Chaque prompt injecte : ton, niveau d'expertise, audience, langue, `aiInstructions` du domaine, et **les sujets exclus comme contrainte explicite**.

Tests : le prompt contient bien les consignes du domaine ; un domaine avec `excludedTopics` produit un prompt qui les nomme ; le marqueur attendu par `FakeAIProvider` est présent.

- [ ] **Step 2 : Validation de l'outline (tests d'abord)**

```ts
validateOutline(markdown: string, domain: Domain): OutlineValidation
// { valid: true, outline: Outline } | { valid: false, reason: string }
```

Règles : exactement un H1 ; au moins deux H2 ; pas de saut de niveau (H2 → H4) ; pas de titre vide ; longueur totale raisonnable ; aucun titre n'aborde frontalement un sujet exclu du domaine.

Utilise `parse` et `extractHeadings` du module `markdown/` — **n'écris pas d'expression régulière sur le Markdown brut**, un `#` dans un bloc de code n'est pas un titre.

Tests : chaque règle violée isolément, plus un plan valide.

- [ ] **Step 3 : `AITaskService`**

```ts
generateTopics(domain, count): Promise<TopicDraft[]>
generateOutline(domain, topic): Promise<Outline>    // valide, relance une fois si invalide
generateDraft(domain, topic, outline): Promise<string>
```

`generateOutline` relance **une seule fois** en renvoyant le défaut au modèle, puis échoue proprement. Réessayer indéfiniment un modèle qui ne comprend pas brûle des minutes pour rien.

Tests avec `FakeAIProvider` : le chemin nominal, la relance sur plan invalide (via `AI_FAKE_INVALID_OUTLINE`), l'échec après la relance.

## Task 4 : Machine à états du pipeline

**Files:** `apps/api/src/pipeline/{pipeline-steps,step-handler}.ts` + specs

- [ ] **Step 1 : Déclaration des étapes**

```ts
interface StepDefinition {
  type: StepType
  order: number
  executable: boolean
  skipReason?: string      // obligatoire si executable === false
}
```

`RESEARCH`, `ANALYSIS`, `FACT_CHECK`, `QUALITY` sont **déclarées non exécutables** avec leur raison — par exemple « aucun fournisseur de recherche avant le Lot 4 ». `OUTLINE`, `DRAFT`, `SEO` sont exécutables.

Test : toute étape non exécutable a une raison non vide. C'est ce qui empêche qu'une étape soit sautée sans que l'utilisateur sache pourquoi.

- [ ] **Step 2 : `StepHandler`**

```ts
interface StepHandler<I, O> {
  readonly type: StepType
  buildInput(run: PipelineRun, previous: StepOutputs): I
  execute(input: I, ctx: StepContext): Promise<O>
}
```

`buildInput` porte la réutilisation du contexte : `DraftStepHandler.buildInput` **lit l'`OUTLINE` déjà persisté** au lieu de le recalculer. C'est ce qui rend le rejeu d'une étape possible sans refaire les précédentes.

Trois handlers : `OutlineStepHandler`, `DraftStepHandler`, `SeoStepHandler` (qui appelle l'analyseur déterministe, **sans aucune IA**).

- [ ] **Step 3 : Commit** — `feat(pipeline): déclaration des étapes et contrat de handler`

## Task 5 : Orchestration, file BullMQ et worker

**Files:** `apps/api/src/pipeline/{pipeline.service,pipeline.processor,pipeline.module}.ts`, `apps/api/src/worker.ts` + tests d'intégration

- [ ] **Step 1 : Tests d'intégration (ils doivent échouer)**

Avec `FakeAIProvider` :
- Un pipeline complet passe `OUTLINE` → `DRAFT` → `SEO` et termine en `WAITING_REVIEW`.
- Les étapes non exécutables sont persistées `SKIPPED` **avec leur raison**.
- L'article est créé en `DRAFT` **avant** le premier appel IA, donc visible immédiatement.
- **Un instantané de version est créé avant chaque écriture automatique** — vérifie-le en comptant les versions.
- **L'IA n'atteint jamais `PUBLISHED`** : à la fin, l'article est en `DRAFT` ou `REVIEW`, jamais au-delà.
- Rejouer `DRAFT` crée `attempt = 2` et **ne recrée pas** l'`OUTLINE` — vérifie que l'`AIJob` d'outline n'est pas dupliqué.
- Un échec (`AI_FAKE_FAIL_STEP=DRAFT`) laisse le run en `FAILED` avec l'erreur persistée, et l'`OUTLINE` reste `COMPLETED`.
- Un double appel à `generateArticle` sur le même topic renvoie **le même run**, et ne crée pas deux articles.
- Annuler un run en cours l'arrête et le marque `CANCELLED`.
- Un non-membre du domaine ne peut ni lancer, ni lire, ni annuler.
- Confusion de domaine fermée, comme pour les autres entités.

- [ ] **Step 2 : Implémenter**

Files BullMQ : `pipeline` avec **concurrence 1**. `jobId = ${stepId}:${attempt}` pour l'idempotence.

Chaque étape, dans une transaction : marquer `RUNNING`, exécuter, persister `output`, marquer `COMPLETED`, enfiler la suivante. Le `correlationId` est propagé dans les données du job et retrouvé dans les logs du worker.

**Reprise après crash** : au démarrage, repasser en `PENDING` tout `PipelineStep` resté `RUNNING` sans job actif dont le `heartbeatAt` est périmé. Sinon un arrêt brutal fige des pipelines pour toujours.

`apps/api/src/worker.ts` cesse d'être un squelette : il enregistre les processeurs.

- [ ] **Step 3 : Commit** — `feat(pipeline): orchestration, file BullMQ et reprise après crash`

## Critères d'acceptation

- [ ] Un pipeline complet produit un article rempli à partir d'un topic, avec `FakeAIProvider`
- [ ] Les étapes non exécutables sont visibles **avec leur raison**, jamais présentées comme réussies
- [ ] Une version est créée avant chaque écriture automatique
- [ ] L'IA n'atteint jamais `PUBLISHED`, vérifié en intégration **et** en E2E
- [ ] Rejouer `DRAFT` ne recalcule pas `OUTLINE`
- [ ] Un double-clic ne crée ni deux runs ni deux articles
- [ ] Le score SEO du pipeline vient de l'analyseur déterministe, jamais du modèle
- [ ] Un prompt contenant `; rm -rf /` n'exécute rien
- [ ] La file affiche position et estimation, ou « indisponible » faute d'historique
- [ ] Le test de fumée du vrai CLI existe et est exclu de la CI
- [ ] `pnpm lint && pnpm typecheck && pnpm test` passent ; CI verte
